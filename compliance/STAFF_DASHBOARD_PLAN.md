# Staff Dashboard — plan & decisions

**Date:** 2026-07-16
**Goal:** open the counsellor dashboard to all teaching staff of a school, not
just the (single, shared) guidance-counsellor account. Rename it **Staff
Dashboard**. Staff are individual accounts.

## Owner decisions (2026-07-16)

| Question | Decision |
|----------|----------|
| How does a teacher get staff access? | **Per-school staff code.** A GC/admin generates a secret code for the school; a teacher redeems it to gain `role: 'staff'`. |
| Do staff see welfare-sensitive data (private notes, DEIS/At-risk flags)? | **Full parity with GC** — staff see exactly what a GC sees. |
| Which students does a teacher see? | **Whole school** (like a GC). No per-class model. |

"Full parity" is the key simplifier: `staff` is functionally identical to `gc`.
This is a **role-generalisation + provisioning** job, not a permission-tiering
one. There is no GC-exclusive surface.

## Trust anchor (why a code, not self-assertion)

Staff see *all* students' data, so — unlike the deferred student school-binding
(H-2) — staff binding cannot be self-asserted. The staff code is the anchor:
- The code lives in `gcSettings/{school}.staffCode`, generated by a GC/admin
  from the dashboard (GC-only write, already rules-protected).
- Redemption goes through a Cloud Function `claimStaffAccess({ school, code })`
  that verifies the code **server-side** and sets `role: 'staff'` + `school` on
  the caller's user doc via the Admin SDK. `role` is client-immutable in the
  rules, so a client can never self-assign `staff`.
- The code is a shared secret; a GC can rotate it (regenerate) at any time.

## Work breakdown

### 1. Role foundation (`staff` becomes a first-class role, full GC parity)
- `utils/authUtils.ts` — add `'staff'` to the `SessionUser.role` union; add an
  `isSchoolStaff(role)` helper (`role === 'gc' || role === 'staff'`).
- `contexts/AuthContext.tsx` — recognise `role: 'staff'`; skip student-only
  auto-notifications for staff as it does for GC.
- `components/AppRouter.tsx` — route `staff` (with a school) to the dashboard.
- `App.tsx` — the ~7 `role !== 'gc'` / `role === 'gc'` guards become
  `!isSchoolStaff(role)` / `isSchoolStaff(role)` so staff get the dashboard
  chrome, not the student chrome.
- `components/GCDashboard.tsx` — the student list excludes `staff` as well as
  `gc`/`admin`.
- `functions/src/islandProjection.ts` + `index.ts` — the peer-island projection
  excludes `staff` (staff are not students).

### 2. Rules generalisation (`firestore.rules`)
- `isGC()` → `isSchoolStaff()` (role is `gc` **or** `staff`); `gcSchool()` →
  `callerSchool()`. Every GC-scoped collection now admits staff of the same
  school. Purely additive — existing GC access is unchanged.
- New collections (below) gated on `isSchoolStaff()` + same school.

### 3. Provisioning
- Cloud Function `claimStaffAccess` (see trust anchor).
- Dashboard **Staff access** panel: view/copy/regenerate the school's staff code.
- LoginPage **Staff** view: register-or-sign-in + redeem code in one flow.

### 4. Rename
- User-facing "Guidance Counsellor / GC Dashboard" → "Staff Dashboard".
  Collection names + route ids stay `gc*` (no data migration; internal only).

## Bundled security follow-ups (done in the same effort)

## Deploy ordering (pre-launch = empty prod, so low risk, but for the record)

Hosting auto-deploys from `main`; **Functions and rules do not**. Deploy order:
1. `firebase deploy --only firestore:rules` (additive; safe first).
2. `firebase deploy --only functions` (claimStaffAccess + teach-back trigger).
3. Hosting (automatic on push to `main`).
The staff feature is inert until 1+2 are deployed; existing GC access is never
affected. Owner should smoke-test rules in the emulator before deploying.
